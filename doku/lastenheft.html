# Lastenheft – Persönliche Entwickler-Website ## 1. Allgemeine Angaben **Projektname:** Persönliche Entwickler-Website / Developer Portfolio **Projektart:** Persönliche Webpräsenz / Portfolio **Auftraggeber:** Steven Heinze **Projektziel:** Entwicklung einer modernen, responsiven und technisch professionellen Website zur persönlichen Präsentation als Anwendungsentwickler. --- # 2. Ausgangssituation Die Website soll als persönliche digitale Visitenkarte und gleichzeitig als Entwickler-Portfolio dienen. Neben der persönlichen Vorstellung sollen insbesondere der berufliche Werdegang, technische Kenntnisse, eigene Softwareprojekte sowie die persönliche Weiterentwicklung dargestellt werden. Die Website soll dabei nicht lediglich einen klassischen Lebenslauf digital abbilden. Sie soll vielmehr einen Einblick in die Person, die technische Arbeitsweise, bisherige Projekte und den individuellen Entwicklungsprozess geben. Ein besonderer Bestandteil soll ein **Development Journal / Entwickler-Tagebuch** sein, in dem Lernfortschritte, Projekterfahrungen, technische Erkenntnisse und wichtige Entwicklungsschritte dokumentiert werden können. Die Website selbst soll ebenfalls als eigenes Softwareprojekt betrachtet und kontinuierlich weiterentwickelt werden. --- # 3. Zielsetzung Die Website soll folgende Hauptziele erfüllen: 1. Professionelle Präsentation der eigenen Person als Anwendungsentwickler. 2. Darstellung des beruflichen Werdegangs. 3. Darstellung technischer Fähigkeiten und verwendeter Technologien. 4. Präsentation eigener Software- und Webprojekte. 5. Transparente Darstellung des Entwicklungsfortschritts eigener Projekte. 6. Darstellung der eigenen Persönlichkeit und Freizeitinteressen. 7. Dokumentation des persönlichen Lern- und Entwicklungsprozesses. 8. Bereitstellung von Kontaktmöglichkeiten. 9. Präsentation einer professionellen und modernen Benutzeroberfläche. 10. Umsetzung der Website als eigenständiges Entwicklungsprojekt. 11. Erweiterbarkeit für zukünftige Funktionen und Inhalte. --- # 4. Zielgruppen Die Website richtet sich insbesondere an: ### Primäre Zielgruppen * potenzielle Arbeitgeber * Personalverantwortliche * technische Recruiter * Unternehmen aus der IT-Branche * potenzielle Auftraggeber ### Sekundäre Zielgruppen * andere Entwickler * Personen aus dem technischen Umfeld * Freunde und Bekannte * Personen mit Interesse an Softwareentwicklung Die Website muss deshalb sowohl für technisch versierte Besucher als auch für Personen ohne tiefgehende Programmierkenntnisse verständlich sein. --- # 5. Inhaltliche Anforderungen ## 5.1 Startseite Die Startseite bildet den ersten Kontaktpunkt mit dem Besucher. Sie soll enthalten: * Name * Berufsbezeichnung * kurze persönliche Vorstellung * kurze Beschreibung der beruflichen bzw. technischen Ausrichtung * ausgewählte Technologien * Verlinkung zu den wichtigsten Bereichen * Verlinkung zu ausgewählten Projekten * Kontaktmöglichkeit Die Startseite soll innerhalb weniger Sekunden vermitteln: > Wer bin ich, was mache ich und woran arbeite ich? --- # 6. Bereich „Über mich“ Der Bereich „Über mich“ soll die Person hinter dem Entwicklerprofil vorstellen. ## 6.1 Kurzprofil Darstellung von: * persönlichem Hintergrund * beruflicher Ausrichtung * Motivation für Softwareentwicklung * persönlichen Interessen im technischen Bereich * individuellen Stärken ## 6.2 Beruflicher Werdegang Der berufliche Werdegang soll chronologisch dargestellt werden. Mögliche Informationen: * Ausbildungsweg * berufliche Stationen * Tätigkeiten * relevante Erfahrungen * Weiterbildungen * wichtige Entwicklungsschritte Die Darstellung soll vorzugsweise als Timeline umgesetzt werden. Beispiel: ```text 2026 │ ├── Position / Projekt │ Beschreibung │ 2025 │ ├── Position / Projekt │ Beschreibung │ 2024 │ └── ... ``` --- # 7. Bereich „Skills & Technologien“ Die technischen Fähigkeiten sollen strukturiert dargestellt werden. Die Skills sollen nach Kategorien gegliedert werden. ## 7.1 Programmiersprachen Beispielsweise: * JavaScript * TypeScript * Python * C# * weitere zukünftig erlernte Sprachen ## 7.2 Webtechnologien Beispielsweise: * HTML * CSS * JavaScript * Frameworks * Node.js * APIs ## 7.3 Datenbanken Darstellung der verwendeten bzw. erlernten Datenbanksysteme. ## 7.4 Tools Beispielsweise: * Git * GitHub * VS Code * Linux * Docker * weitere Entwicklungswerkzeuge ## 7.5 Konzepte Beispielsweise: * objektorientierte Programmierung * Responsive Design * REST APIs * Datenbanken * Versionsverwaltung * Testing * Clean Code * Softwarearchitektur Die Website soll keine unrealistischen Prozentwerte verwenden, wenn diese keine objektive Aussagekraft besitzen. Stattdessen soll der Entwicklungsstand beispielsweise über folgende Kategorien dargestellt werden: * **Aktiv im Einsatz** * **Fortgeschritten** * **In Vertiefung** * **Grundkenntnisse** * **Geplant** --- # 8. Bereich „Projekte“ Der Projektbereich stellt einen zentralen Bestandteil der Website dar. Alle relevanten eigenen Projekte sollen übersichtlich dargestellt werden. Jedes Projekt soll mindestens folgende Informationen enthalten: * Projektname * Kurzbeschreibung * Ziel des Projekts * Projektstatus * Entwicklungszeitraum * verwendeter Techstack * Projektbeschreibung * verwendete Technologien * wichtige Entwicklungsphasen * aktuelle Fortschritte * persönliche Lernerfahrungen * gegebenenfalls Screenshots * gegebenenfalls Live-Demo * gegebenenfalls GitHub-Repository --- # 9. Projekt-Ampelsystem Für jedes Projekt soll ein einheitliches Statussystem verwendet werden. ### Statusdefinition 🟢 **Abgeschlossen** Die entsprechende Phase oder Funktion wurde erfolgreich umgesetzt. 🟡 **In Arbeit** Die entsprechende Phase befindet sich aktuell in Entwicklung. 🔴 **Offen** Die Phase wurde noch nicht begonnen bzw. ist noch nicht umgesetzt. ⚪ **Nicht geplant** Die Funktion oder Phase ist für das Projekt nicht vorgesehen. Beispiel: ```text Projekt: KIEZFIT Konzeption 🟢 HTML 🟢 CSS 🟢 Responsive Design 🟢 JavaScript 🟡 Backend 🔴 Datenbank 🔴 Testing 🔴 Deployment 🟢 Dokumentation 🟡 ``` Das System soll so gestaltet werden, dass zukünftige Projekte dieselbe Struktur verwenden können. --- # 10. Projekt-Detailseiten Bei größeren Projekten soll eine eigene Detailansicht möglich sein. Eine Projektseite soll beispielsweise folgende Struktur besitzen: ```text Projekt │ ├── Übersicht ├── Zielsetzung ├── Anforderungen ├── Konzept ├── Design ├── Entwicklung ├── Techstack ├── Fortschritt ├── Herausforderungen ├── Lösungen ├── Erkenntnisse └── Ergebnis ``` Dadurch soll nicht nur das fertige Ergebnis gezeigt werden, sondern auch der Weg dorthin. --- # 11. Bereich „Meine Entwicklung“ Dieser Bereich soll die persönliche Weiterentwicklung als Entwickler darstellen. Mögliche Inhalte: ### Aktuelles Lernen * aktuell erlernte Programmiersprachen * Frameworks * Tools * Konzepte * Technologien ### Zukünftige Lernziele * geplante Technologien * geplante Projekte * gewünschte Weiterbildungen * persönliche Entwicklungsziele ### Entwicklungsfortschritt Der Fortschritt soll regelmäßig aktualisiert werden können. --- # 12. Bereich „Wie ich entwickle“ Dieser Bereich soll die persönliche Arbeitsweise darstellen. Der Entwicklungsprozess soll beispielsweise folgendermaßen dargestellt werden: ```text Idee ↓ Anforderungen ↓ Konzeption ↓ Planung ↓ Design / Architektur ↓ Implementierung ↓ Testing ↓ Optimierung ↓ Deployment ↓ Dokumentation ``` Ziel ist es, dem Besucher einen Einblick in die eigene Vorgehensweise bei Softwareprojekten zu geben. --- # 13. Bereich „Entwicklungsumgebung“ Optional soll die persönliche Entwicklungsumgebung dargestellt werden. Mögliche Inhalte: * Betriebssystem * Entwicklungsumgebung * Code-Editor * Terminal * Versionsverwaltung * verwendete Tools * Serverumgebung * Deployment-Technologien Dieser Bereich soll einen authentischen Einblick in die tägliche Entwicklungsarbeit geben. --- # 14. Bereich „Über mich als Person“ Neben der technischen Präsentation soll auch die Persönlichkeit dargestellt werden. Mögliche Inhalte: ## Freizeit * Sport * Gaming * technische Projekte * sonstige Freizeitaktivitäten ## Interessen * Softwareentwicklung * Technologie * Linux * Hardware * Gaming * Server / Selfhosting * Game Development * Open Source * neue Programmiersprachen Die Inhalte sollen authentisch und persönlich gestaltet werden und nicht wie ein weiterer Lebenslauf wirken. --- # 15. Bereich „Development Journal“ Das Entwickler-Tagebuch bildet einen wichtigen Bestandteil der Website. Es soll ermöglichen, regelmäßig kurze Beiträge über die eigene Entwicklung zu veröffentlichen. Mögliche Inhalte eines Eintrags: * Datum * Titel * Projekt * Thema * Beschreibung * technische Erkenntnisse * Probleme * gefundene Lösungen * persönliche Erkenntnisse * verwendete Technologien Beispiel: ```text 17.08.2026 KIEZFIT – Mobile Navigation Heute wurde die mobile Navigation fertiggestellt. Dabei habe ich gelernt: - ... - ... - ... ``` Das Journal soll langfristig eine chronologische Entwicklung der eigenen Fähigkeiten dokumentieren. --- # 16. Journal-Kategorien Um das Tagebuch langfristig übersichtlich zu halten, sollen Einträge kategorisiert werden können. Beispielsweise: * Projekte * JavaScript * Webentwicklung * Backend * Linux * Git * Server * Lernen * Fehler & Lösungen * persönliche Erkenntnisse Optional soll später eine Filter- oder Suchfunktion implementiert werden. --- # 17. Kontaktbereich Die Website muss eine klare Kontaktmöglichkeit bereitstellen. Mögliche Kontaktmöglichkeiten: * E-Mail * GitHub * LinkedIn * weitere berufliche Plattformen * optional Kontaktformular Zusätzlich kann ein Lebenslauf als PDF bereitgestellt werden. --- # 18. Navigation Die Website soll über eine übersichtliche Hauptnavigation verfügen. Vorgeschlagene Struktur: ```text Start Über mich Skills Projekte Entwicklung Journal Kontakt ``` Die Navigation soll: * auf Desktop-Geräten übersichtlich dargestellt werden * auf mobilen Geräten angepasst werden * eine klare Orientierung ermöglichen * bei längeren Seiten gegebenenfalls als Sticky Navigation umgesetzt werden --- # 19. Responsive Design Die Website muss vollständig responsive sein. Sie soll mindestens folgende Gerätegruppen berücksichtigen: * Desktop * Laptop * Tablet * Smartphone Die Inhalte sollen sich automatisch an unterschiedliche Bildschirmgrößen anpassen. Besondere Aufmerksamkeit ist auf folgende Punkte zu legen: * Navigation * Projektkarten * Timeline * Tabellen * Techstack-Darstellung * Bilder * Journal-Einträge * Abstände * Schriftgrößen Horizontales Scrollen aufgrund fehlerhafter Layouts soll vermieden werden. --- # 20. Designanforderungen Das Design soll modern, technisch und professionell wirken. Gleichzeitig soll die Website persönlich und nicht wie eine generische Unternehmenswebsite wirken. Gewünscht sind: * klare Typografie * ausreichender Weißraum * gute visuelle Hierarchie * dezente Animationen * moderne Karten- und Komponentenstruktur * konsistente Farben * klare Statusanzeigen * gute Lesbarkeit Technische Elemente dürfen bewusst als Gestaltungselement verwendet werden. Beispielsweise: * Code-Optik * Terminal-Elemente * Statusanzeigen * technische Timeline * Git-ähnliche Darstellungen * Fortschrittsindikatoren Diese Elemente sollen jedoch sparsam eingesetzt werden und nicht zulasten der Benutzerfreundlichkeit gehen. --- # 21. Benutzerfreundlichkeit Die Website soll intuitiv bedienbar sein. Besucher sollen schnell zu folgenden Informationen gelangen: 1. Wer bin ich? 2. Was kann ich? 3. Welche Projekte habe ich umgesetzt? 4. Wie arbeite ich? 5. Was lerne ich aktuell? 6. Wie kann man mich kontaktieren? Die wichtigsten Informationen sollen ohne unnötige Navigation erreichbar sein. --- # 22. Barrierefreiheit Die Website soll grundlegende Anforderungen an Barrierefreiheit berücksichtigen. Dazu gehören unter anderem: * ausreichende Kontraste * verständliche Überschriftenstruktur * semantisches HTML * sinnvolle Alt-Texte * Tastaturbedienbarkeit * sichtbare Fokuszustände * verständliche Linktexte * keine wichtigen Informationen ausschließlich über Farbe vermitteln Insbesondere beim Ampelsystem müssen die Statusinformationen zusätzlich durch Text oder Symbole erkennbar sein. --- # 23. Technische Anforderungen Die konkrete technische Umsetzung soll im Pflichtenheft festgelegt werden. Grundsätzlich soll die Website: * performant sein * modular aufgebaut sein * wartbar sein * erweiterbar sein * sauberen Code verwenden * eine nachvollziehbare Projektstruktur besitzen * Versionsverwaltung verwenden Die Website soll selbst als Referenzprojekt für die eigenen Entwicklungskenntnisse dienen. --- # 24. Erweiterbarkeit Die Architektur soll spätere Erweiterungen ermöglichen. Mögliche zukünftige Funktionen: * dynamische Projektverwaltung * Datenbank * Content Management System * dynamisches Development Journal * Suchfunktion * Kategorien und Filter * Login für Administration * Analytics * API-Anbindung * Kommentare * Newsletter * Mehrsprachigkeit * Dark-/Light-Mode * automatisierte Deployment-Prozesse Diese Funktionen sind zunächst **nicht Bestandteil der Basisversion**, sollen aber bei der technischen Planung berücksichtigt werden. --- # 25. SEO Die Website soll technisch für Suchmaschinen optimiert werden. Dazu gehören unter anderem: * aussagekräftiger Seitentitel * Meta Description * semantische HTML-Struktur * sinnvolle Überschriften * sprechende URLs * Alt-Texte * strukturierte Inhalte * schnelle Ladezeiten --- # 26. Performance Die Website soll möglichst schnell geladen werden. Zu berücksichtigen sind: * optimierte Bilder * minimierte Ressourcen * effiziente CSS- und JavaScript-Strukturen * Vermeidung unnötiger Bibliotheken * Lazy Loading bei geeigneten Inhalten * möglichst geringe Abhängigkeiten --- # 27. Sicherheit Falls später dynamische Funktionen oder ein Backend eingesetzt werden, müssen grundlegende Sicherheitsmaßnahmen berücksichtigt werden. Dazu gehören unter anderem: * sichere Authentifizierung * Schutz sensibler Daten * sichere Passwortspeicherung * Eingabevalidierung * Schutz vor XSS * Schutz vor SQL Injection * sichere API-Kommunikation * HTTPS * regelmäßige Updates Für die reine statische Basisversion ist kein Login-System erforderlich. --- # 28. Deployment Die Website soll auf einem öffentlich erreichbaren Webserver betrieben werden können. Vorgesehen sind: * eigene Domain * HTTPS * Webserver * Versionsverwaltung * gegebenenfalls automatisiertes Deployment Der Deployment-Prozess soll später Bestandteil der Projektdokumentation werden. --- # 29. Versionsverwaltung Das Projekt soll mit Git verwaltet werden. Das Repository soll eine nachvollziehbare Entwicklung ermöglichen. Commit-Nachrichten sollen sinnvoll und verständlich formuliert werden. Optional können später eingesetzt werden: * Branches * Pull Requests * Issues * Tags / Releases * GitHub Projects * CI/CD --- # 30. Dokumentation Das Projekt soll dokumentiert werden. Die Dokumentation soll mindestens enthalten: * Projektbeschreibung * Zielsetzung * verwendete Technologien * Projektstruktur * Entwicklungsphasen * Installations- bzw. Deploymentinformationen * wichtige Entscheidungen * bekannte Einschränkungen Zusätzlich soll das Development Journal die laufende Entwicklung dokumentieren. --- # 31. Abgrenzung Basisversion Die erste Version soll sich auf die wesentlichen Funktionen konzentrieren. ### Bestandteil der Basisversion * Startseite * Über mich * beruflicher Werdegang * Skills * Projekte * Projekt-Ampelsystem * persönliche Interessen * Development Journal * Kontakt * responsive Design * grundlegende SEO * Git-Versionsverwaltung * Deployment ### Nicht Bestandteil der ersten Version * Benutzerverwaltung * Login * Datenbank * CMS * komplexes Backend * Kommentare * Newsletter * komplexe Analytics * Social-Media-Feed Diese Funktionen können später in weiteren Entwicklungsphasen ergänzt werden. --- # 32. Entwicklungsphasen Das Projekt soll schrittweise entwickelt werden. ## Phase 1 – Konzeption * Anforderungen festlegen * Seitenstruktur entwickeln * Inhalte planen * Designrichtung festlegen * technische Grundlagen festlegen ## Phase 2 – Grundstruktur * Projekt erstellen * HTML-Struktur * Navigation * Seitenbereiche * grundlegende CSS-Struktur ## Phase 3 – Design * Layout * Farben * Typografie * Komponenten * Karten * Timeline * Statussystem ## Phase 4 – Responsive Design * Desktop * Tablet * Smartphone * Navigation * mobile Optimierung ## Phase 5 – JavaScript / Interaktion * Navigation * Animationen * Filter * Statusanzeigen * interaktive Komponenten ## Phase 6 – Projekte * Projektübersicht * Projektkarten * Projektstatus * Detailseiten * Techstacks ## Phase 7 – Development Journal * Journal-Struktur * Beiträge * Kategorien * Filter * chronologische Darstellung ## Phase 8 – Optimierung * Performance * Accessibility * SEO * Browserkompatibilität * Codequalität ## Phase 9 – Deployment * Server * Domain * HTTPS * Deployment * abschließende Tests ## Phase 10 – Weiterentwicklung Nach Veröffentlichung wird die Website kontinuierlich erweitert. --- # 33. Erfolgskriterien Das Projekt gilt in seiner Basisversion als erfolgreich umgesetzt, wenn: * die Website öffentlich erreichbar ist * alle vorgesehenen Kernbereiche vorhanden sind * die Website auf Desktop, Tablet und Smartphone funktioniert * die Navigation zuverlässig funktioniert * die Projekte übersichtlich dargestellt werden * das Ampelsystem verständlich funktioniert * der berufliche Werdegang nachvollziehbar dargestellt wird * technische Fähigkeiten strukturiert dargestellt werden * persönliche Interessen vorhanden sind * das Development Journal integriert ist * eine Kontaktmöglichkeit vorhanden ist * die Website technisch sauber strukturiert ist * das Projekt über Git versioniert wird * grundlegende SEO- und Accessibility-Anforderungen erfüllt sind * die Website selbst als professionelles Portfolio-Projekt vorzeigbar ist --- # 34. Langfristige Vision Die Website soll sich langfristig von einer einfachen Portfolioseite zu einer persönlichen **Developer Platform** entwickeln. Sie soll nicht nur zeigen, was bereits erreicht wurde, sondern kontinuierlich dokumentieren: **Woher ich komme → was ich aktuell kann → woran ich arbeite → was ich lerne → wohin ich mich entwickle.** Damit bildet die Website gleichzeitig: * persönliche Website * Entwicklerportfolio * digitalen Lebenslauf * Projektdokumentation * Lernplattform * Development Journal * technische Visitenkarte und langfristig eine Dokumentation der eigenen Entwicklung als Anwendungsentwickler. # 35. Grundprinzip des Projektes Die Website soll nach folgendem Prinzip aufgebaut werden: > **Nicht nur fertige Ergebnisse zeigen, sondern den Weg dorthin sichtbar machen.** Dadurch soll der Besucher nicht nur sehen, **welche Technologien eingesetzt wurden**, sondern auch nachvollziehen können, **wie Projekte geplant, entwickelt, verbessert und abgeschlossen werden**. Die Website selbst wird damit zum ersten und dauerhaft weiterentwickelten Portfolio-Projekt.
